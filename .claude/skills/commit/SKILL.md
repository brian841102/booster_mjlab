# commit：整理代码并提交

四个步骤依次进行，**每一步结束都停下来等用户**，不要跳步，也不要替用户做第 2、4 步的决定。回复用简体中文。

## 第 1 步：把目前的更动分类

1. 收集全部更动：`git status --short`、`git diff`（已跟踪）、未跟踪文件逐个看内容；与上一次提交（`git log --oneline -10`）对照，确认范围。
2. 按"功能 / 实验"把 hunk 分组（一个文件可以拆到多组），每组写清楚：做了什么、涉及哪些文件、服务于哪个实验（Exp 编号）或哪个目标。
3. 分三类，**每条都要给依据**——实验记录 `tools/nemov3_finetune.md` 里的结论、评估数字或用户原话；没有依据的不能归为"有效"：
   - **对目标有效**：有实验证明它带来了想要的结果（写出对照实验与数字）。
   - **对目标无效**：实验证明没用、有害，或者被后来的做法取代。
   - **是否有效待验证**：还没做对照实验、结果混合（例如一项变好一项变差），或只是工具 / 基础设施、无法用实验判断。
4. 另外单独列出：评估 / 可视化工具（说明未来是否可能还要用）、文档、只在 scratchpad 或 `logs/` 下的临时脚本（不提交）。
5. 用表格呈现：`| # | 更动 | 文件 | 相关实验 | 依据 | 分类 |`，最后给出我的建议（保留 / 移除），然后**停下来等用户决定**。

## 第 2 步：用户决定去留

1. 用户逐项决定。有疑问的项先问清楚，不要自己猜。
2. **移除前先备份**：`logs/<主题>_backup_<日期>/` 下存 `uncommitted.diff`（`git diff`）和未跟踪文件的 `untracked.tgz`（`logs/` 已被 gitignore，不会提交）。
3. 按决定移除代码后检查：
   - 所有保留下来的任务都能注册、载入（`load_env_cfg` / `load_rl_cfg`）；
   - 保留实验的任务设定与对应 run 目录下的 `params/env.yaml`、`params/agent.yaml` 逐项一致（只差执行期字段；比较 repr 时去掉 ` at 0x...` 内存地址）；
   - 之前已提交的任务设定没有被改到；
   - 相关的检查脚本（例如 `tools/nemov3_tools/symmetry_check.py`）通过。
4. 被移除的实验只在 `tools/nemov3_finetune.md` 里留记录，并注明"代码已移除、备份位置"。
5. 报告检查结果，进入第 3 步。

## 第 3 步：提交计划

1. **按开发逻辑排序**：底层 / 通用基础设施 → 机器人模型 → 环境与奖励（mdp）→ 任务配置与注册 → 评估工具 → 文档。后面的提交可以依赖前面的，反之不行；每个提交单独检出时都应能导入、不报错。
2. **命名规范（Conventional Commits）**：标题（`type(scope): subject`）用英文，正文用简体中文；`<type>(<scope>): <subject>`
   - type：`feat` 新功能、`fix` 修 bug、`refactor` 不改行为的重构、`chore` 工具 / 杂项、`docs` 文档、`test` 测试；
   - scope：模块名，例如 `amp`、`velocity`、`nemov3`、`tools`；
   - subject：祈使句、小写开头、不加句号、≤ 72 字符；
   - 正文（简体中文）：说明为什么改、改了什么，引用实验编号与关键结果。
3. 每个提交列出：提交信息（标题 + 正文）、包含的文件（一个文件拆到多个提交时，写明各自包含哪些 hunk）。
4. 检查不该提交的东西：论文 PDF、大文件、`logs/`、scratchpad、密钥；本仓库是公开 fork，不用 Git LFS。
5. 呈现计划后**停下来讨论**。用户要求修改时，改完重新呈现整个计划。

## 第 4 步：批准后自动提交

1. 只有用户**明确批准**（例如"提交吧""批准"）才执行。
2. 按计划顺序逐个提交：
   - 只 `git add` 计划列出的路径；一个文件分到多个提交时，用 `git add -p` 的等价做法（生成对应 hunk 的 patch，`git apply --cached`）；
   - 提交信息先写到 scratchpad 的文件里，再用 `git commit -F <文件>`；
   - 提交信息结尾加上当前会话 system reminder 里给出的署名行（Co-Authored-By / Claude-Session）；
   - 每个提交后确认 `git status` 与预期一致。
3. 全部完成后给出 `git log --oneline`（本次新增的提交）和剩余未提交的更动（应为空，或只剩用户决定不提交的）。
4. **不推送（push）**，除非用户另外要求。
